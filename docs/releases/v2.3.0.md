# RAHP Toolkit v2.3.0 — Common Five-ring

**Release date:** 2026-09-13  
**Theme:** Portable Coverage and Source-Preserving Assurance  
**Codename:** Common Five-ring (*Ypthima baldus*)

## Release summary

v2.3.0 is a coordinated minor release that packages the post-v2.2 assurance work into a stable, externally readable boundary. The principal change is not a broader claim of safety; it is a stronger ability to say exactly **what proposition is being assessed, what evidence supports it, what remains unknown, who owns the residual, and what event should trigger reassessment**.

The release retains the v1 engine family and normalized result/evidence contracts. It is additive at the toolkit-product layer.

## Major advances

### Portable capability coverage

RAHP now has a generic capability-coverage model that can express coverage, evidence maturity, stale-evidence reassessment and residual ownership without embedding the semantics of a particular consumer in the core engine. Persona and Data Rooms are concrete qualification consumers of this mechanism.

### Current implementation and composition evidence

The post-v2.2 tranche reconciles current VTI/OpenVTC implementation evidence for bounded action-time, resolved-effect, credential replay, privacy and related composition propositions. These observations are deliberately proposition-scoped: an exercised PASS does not imply implementation-wide or portfolio-wide GREEN.

### Data Rooms and Persona

Data Rooms and Persona coverage are represented as explicit proposition catalogues with evidence maturity. Current target-native evidence advances supported surfaces while private-room ZK, witnessed anchoring/freshness, migration, operator-control and other unavailable deployment/runtime propositions remain evidence-required or deferred as appropriate.

### Upstream dependency and evidence-debt hygiene

Downstream issues now distinguish locally executable work, external evidence requirements, upstream semantic dependencies and deferred evidence triggers. A proposition whose legitimate A/B implementation or migration experiment does not yet exist remains open as durable evidence debt rather than being closed with a synthetic substitute.

### DRARM / resilience assurance

DRARM findings and review-required signals can now enter RAHP as source-preserving resilience propositions. RAHP records the original rule and target provenance, maps to portable assurance patterns only where an explicit mapping exists, and creates deterministic runtime evidence obligations for higher-assurance claims. Static detector output is evidence triage, not terminal assurance.

## Evidence and claim boundaries

v2.3.0 preserves these non-negotiable invariants:

- missing evidence never becomes PASS;
- workflow success is not assurance success;
- component PASS is not composition PASS;
- normative convergence is not implementation conformance;
- runtime properties require runtime evidence;
- generic RAHP core remains target-agnostic;
- residuals require durable owners;
- source findings are not silently reinterpreted to fit a local model.

Open upstream or deployment dependencies therefore do not invalidate this release. They are part of the truthful terminal state of the affected propositions.

## Coordinated release relationship

This release is coordinated with DPIP v0.2.0 and Trust Protocol Interop Lab v0.6.0. The three repositories remain independently versioned and independently governed:

- **RAHP** owns assurance state, proposition/evidence reconciliation and terminal posture;
- **DPIP** owns composed privacy evaluation and privacy-specific evidence sufficiency;
- **Interop Lab** owns bounded executable cross-protocol and implementation evidence.

Evidence crosses repository boundaries through explicit contracts and provenance rather than shared implicit state.

## Compatibility

No compatibility-family break is introduced:

- `rahp-engine-contract-v1`, revision `1.3`;
- normalized result schema `1`;
- `rahp-evidence-retention-v1`.

Consumers using the stable v1 engine family do not need to reinterpret prior terminal records.

## Upgrade guidance

Existing v2.2 users should update the toolkit/version metadata and regenerate validation outputs as normal. Consumers should adopt the capability-coverage and resilience proposition/evidence surfaces only where relevant. Historical evidence remains historical evidence; do not relabel older results as v2.3 findings without a new source pin or reassessment trigger.

## What this release does not claim

v2.3.0 does not claim universal DTG/OpenVTC conformance, deployment-wide privacy, full Data Rooms private-tier execution, or availability of genuine two-implementation portability/substitution evidence. Those claims remain bounded by their own evidence and ownership records.
